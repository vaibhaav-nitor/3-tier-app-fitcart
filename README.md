# 🚀 FitCart — 3-Tier Application on Azure Kubernetes Service

A 3-tier application deployed to Azure Kubernetes Service, with the Azure
infrastructure defined in Terraform and delivery driven by GitHub Actions and
Helm. Built as a testing environment: the footprint is deliberately small and
simple rather than production-hardened.

---

## 📌 Overview

- **Frontend** — Vite/React SPA served by nginx, which also proxies `/api/` to the backend
- **Backend** — Spring Boot 3.2 REST API on Java 21
- **Database** — Azure Database for PostgreSQL Flexible Server (managed, not in-cluster)

Frontend and backend are each a separate container image, a separate Helm release,
and a separate CI/CD workflow, so a change to one deploys only that one. The
database is provisioned by Terraform alongside the rest of the infrastructure —
there is no in-cluster database chart or release.

## ☁️ Infrastructure (Terraform)

Modular Terraform provisions, in order: resource group → VNet → ACR → Key Vault →
managed PostgreSQL → AKS joined to the VNet subnet, plus the `AcrPull` role
assignment that lets the cluster pull images with no `imagePullSecrets`. The
database is Azure Database for PostgreSQL Flexible Server, reachable over public
access with a scoped firewall rule — not inside the VNet, to avoid adding a
delegated subnet and private DNS zone to a project that has otherwise stayed
deliberately simple.

State lives in an Azure Storage backend created by a one-time `terraform/bootstrap`
run. Full setup instructions — service principal, GitHub secrets, teardown — are
in **[terraform/README.md](./terraform/README.md)**.

## 🔄 CI/CD

Three GitHub Actions workflows:

| Workflow | Trigger | Does |
|---|---|---|
| `terraform.yml` | manual (`plan`/`apply`/`destroy`), plan on PRs | Provisions Azure, including the database |
| `backend-ci-cd.yml` | `backend/**`, `helm/backend/**` | Builds → ACR → deploys |
| `frontend-ci-cd.yml` | `frontend/**`, `helm/frontend/**` | Builds → ACR → deploys |

Each application workflow builds its image, scans it with Trivy (report-only),
pushes it to Azure Container Registry tagged with the commit SHA, then runs
`helm upgrade --install` against the cluster.

The database has to exist before the backend can start — run `terraform apply`
before the first backend deploy on a fresh environment. After that, there is no
separate database deploy step; the backend workflow reads the database's
hostname (`POSTGRES_HOST`, a Terraform output) at deploy time.

## 🔐 Security posture

- Images are pulled via the cluster's managed identity holding `AcrPull` — no registry credentials in Kubernetes
- The Postgres password is generated by Terraform, stored in Azure Key Vault, and read by the deploy workflows at run time — it is not in Git and not a GitHub secret. The same credentials are the database server's actual administrator login, so nothing is duplicated
- The backend connects to the database over TLS (`sslmode=require`) — Flexible Server enforces this and rejects plaintext connections
- The only GitHub secrets are the service principal's `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID`; cluster and registry names are plain repository variables

This is a test environment. The API server, registry and vault are all reachable
over public endpoints — private endpoints and network restrictions were
deliberately left out. See *Not included* below.

---

## 🚦 Getting started

1. Follow [terraform/README.md](./terraform/README.md) to bootstrap state, create the service principal, and `apply` the infrastructure — this creates the database
2. Publish the Terraform outputs (including `POSTGRES_HOST`) as GitHub repository variables
3. Run **Backend**, then **Frontend**
4. `kubectl get svc frontend -n fitcart` gives the public IP
